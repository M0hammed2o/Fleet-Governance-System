# Human UAT execution guide

Status: 27 canonical cases are ready for human execution with synthetic data. Automated rehearsal is not human acceptance and no case has been marked passed or signed off.

## Execution pack

The catalogue remains immutable at `pilot/uat-catalogue.json`. Rehearsal classifications live separately at `pilot/uat-rehearsal-classifications.json`. Initialize a private local execution pack beneath ignored `.data`:

```text
npm run pilot:uat:validate
npm run pilot:uat:execution:init -- .data/uat-execution-pack.json
npm run pilot:uat:execution:validate -- .data/uat-execution-pack.json
npm run pilot:uat:execution:export -- .data/uat-execution-pack.json .data/uat-execution-review.csv
```

Initialization refuses to overwrite a file and creates 27 empty histories. Validation binds the pack to the catalogue SHA-256, requires chronological unique events, evidence for PASS/FAIL, a defect for FAIL, `UAT_TESTER` for result/retest entries and `UAT_APPROVER` for final sign-off. Nothing may follow final sign-off in a pack revision. Accepted packs are review-controlled snapshots; correction requires a new copied revision and retained prior snapshot, never silent editing. The CSV export neutralizes spreadsheet formulas.

The local pack was chosen instead of a new application workflow because Phase 15A needs safe human execution support without introducing unnecessary personal-data storage, identity lifecycle, deployment or a new authorization surface. It uses source/review control and append-only event validation; it is not suitable as a multi-user hosted UAT service.

## Required people and test accounts

Name people only in the private execution pack; approved placeholders such as `SYNTHETIC-UAT-TESTER-01` are allowed during rehearsal. Do not store personal contact details, signatures, credentials or confidential narratives.

- UAT lead coordinates reset, scope, evidence and defects.
- Role testers cover Company Administrator, Dispatch, Gate Security, Approving Manager, Finance, Fleet/GPS, Investigator, External Auditor, Executive and Platform roles.
- Technical/support observer assists without taking over the tester's result.
- Security/privacy reviewer observes isolation, access, evidence and data labels.
- Business approver decides acceptance separately from testers and engineering.

Use only seeded `@pilot.example.test` accounts and credentials generated by the local seed process. Obtain credentials from the approved local output channel; never copy them into the pack or evidence.

## Start and reset

1. Record candidate commit, local/staging-synthetic environment, browser/device and test window.
2. Confirm no real provider/email/payment connection and no real/customer/biometric data.
3. Run the complete engineering gate and review expected blocked production/staging readiness.
4. Locally run `npm run pilot:reset`, `npm run pilot:seed`, then `npm run pilot:verify`. The current guarded seed refuses remote staging; a future staging loader needs separate approval.
5. Initialize the execution pack once. Assign case/role coverage without broadening permissions.
6. Record only non-sensitive evidence references; files remain in approved private/ignored storage.

## Per-case procedure

1. Read objective, role, preconditions, synthetic test data, steps and expected result from the canonical catalogue.
2. Sign in as the exact role; confirm the visible synthetic warning and environment.
3. Execute every step, including the denial/error branch. Do not substitute automated output for observation.
4. Record actual result, environment, PASS/FAIL/BLOCKED, evidence reference, defect reference, comments and timestamp as a new `RESULT_RECORDED` event.
5. PASS means observed outcome matched all material expected behavior. FAIL requires a defect. BLOCKED requires cause, owner and next action; it is not PASS.
6. A different tester performs required retest and appends `RETEST_RECORDED` with the original and adjacent negative path.
7. The approver reviews catalogue, chronology, evidence, open defects, dependencies and decisions, then appends final `SIGN_OFF_RECORDED`.

## Evidence and defects

Evidence may be a safe screenshot, redacted trace/JSON/CSV, command summary, synthetic record ID or audit-event ID. Crop/minimize; never include passwords, tokens, connection strings, biometrics, real identities/locations, raw confidential allegations or unnecessary provider IDs. Use opaque local references in the pack.

Record defects in `PILOT_DEFECT_REGISTER.md`: reproduction, expected/actual, severity, privacy/security effect, workaround, owner, status, fix and independent retest. Critical/High stops acceptance. Medium/Low conditional acceptance requires owner, expiry and rollback trigger.

## Case classification

All 27 cases are `MANUAL_VERIFICATION_REQUIRED` or `PARTIALLY_AUTOMATED`; the classification file additionally marks existing automated evidence, business-owner, provider and legal/privacy dependencies case by case. `AUTOMATED_COVERAGE` means a regression path exists, not that the human case passed. Provider-dependent cases may be rehearsed with synthetic data but cannot accept a real integration. Legal/privacy-dependent cases require the named authorized owner.

## Acceptance states

- `ACCEPTED`: all applicable material outcomes passed; no Critical/High; required decisions/evidence complete.
- `CONDITIONALLY_ACCEPTED`: only owned/dated Medium or Low conditions with explicit expiry/rollback; never provider/legal facts guessed.
- `REJECTED`: material failure, unresolved Critical/High, isolation/privacy failure or unmet non-waivable entry criterion.
- `PENDING`: testing/review is not final.

Business acceptance, security/privacy approval, technical release approval and deployment authorization are distinct. A UAT signature cannot authorize cloud creation, real data, provider terms or production.

## Rollback and recovery

Stop on isolation/privacy breach, misleading synthetic/live label, corrupt history, uncontrolled external delivery or Critical/High defect. Preserve redacted evidence, disable the affected workflow, end/revoke mappings where appropriate, reset only the fixed synthetic tenant under the guarded command, restore the approved candidate/database backup if required, retest, and create a new execution-pack revision. Do not edit an accepted snapshot.
